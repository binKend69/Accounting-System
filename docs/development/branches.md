# فروع التاجر وعزل قواعد التجار

التاريخ: 2026-10-30. القرار: U7 / DEC-005. المتطلبات: REQ-002،004،006،008،019،020،039،040،049. القبول: SC-13. التنفيذ على Feature-account-system.

## الهدف المعتمد

إعادة بناء النظام الموصوف في المصادر، والحفاظ على وظائفه المطلوبة، مع تصحيح أخطاء الحسابات والبيانات، وتوحيد الشاشات المتشابهة وتحسين الواجهات وسهولة الاستخدام. قرار الفروع ينظم تخزين بيانات التاجر ولا يختزل نطاق الوحدات في خطة P01–P12.

لكل تاجر قاعدة SQL Server مستقلة ومنشأة واحدة. تحتوي قاعدة التاجر فروعه، ويكفي فرع واحد لمن لديه محل واحد. لا CompanyId لعزل تجار مختلفين داخل قاعدة مشتركة، ولا اختيار تاجر عالمي قابل للتغيير بين طلبات المستخدمين.

## ما تغير في تأسيس P03

- يبقى CompanyInfo سجلاً واحداً بالهوية 1. حقل BranchId فيه يشير إلى الفرع الأول/الافتراضي للمنشأة، ولا يعني أن كل بيانات المنشأة تتبع ذلك الفرع وحده. لم تضف هذه الحزمة تغيير الفرع الافتراضي.
- يزيل Migration إضافي SupportMerchantBranches قيد BranchId=1، ويحافظ على الجداول والهويات والعلاقات والبيانات السابقة. لم تعدل Migrations السابقة أو الملفات الأصلية.
- تولد SQL Sequence أرقام الفروع بدءاً من أكبر رقم موجود +1. قد تظهر فجوات بعد التراجع أو إعادة تشغيل الخادم؛ رقم الفرع هوية داخلية وليس تسلسلاً محاسبياً خالياً من الفجوات. لا يعاد ترقيم الموجود.
- يستخدم init-company هوية الفرع الفعلية التي أعادها SQL، وينشئ المنشأة والفرع الأول والتدقيق داخل معاملة واحدة. لا يختار اسماً تجارياً أو بيانات منشأة نيابة عن المستخدم.
- يضيف IBranchSetupService وadd-branch فرعاً بعد إعداد منشأة فعالة فقط. يحتاج الطلب إلى مستخدم مخول بـ SETUP.MANAGE. حفظ الفرع وتدقيق BRANCH_CREATED في معاملة واحدة، ويستخدم قفل التأسيس نفسه لمنع التداخل مع إنشاء المنشأة.
- الرجوع إلى Migration السابق يرفض وجود أي فرع أو مرجع منشأة برقم غير 1، بما في ذلك المحذوف منطقياً. عند توافق البيانات، تزال قيمة العمود الافتراضية قبل إزالة Sequence. لا يحذف أي فرع لإجبار الرجوع.

## الفصل بين الفروع وحدود التنفيذ الحالي

فصل قواعد التجار حد مستقل عن تصفية فروع التاجر نفسه. يوجد الآن BranchId للمراكز والمستودعات والحسابات والمستخدمين، وعلاقات FK تمنع الإشارة إلى فرع غير موجود. تبقى المراجع المشتركة للتاجر مثل العملات والوحدات والأدوار داخل قاعدته. الحقول القديمة التي تسمح بفرع NULL محفوظة؛ لا يعني NULL تلقائياً تصريحاً بالوصول إلى كل الفروع.

هذه الحزمة تؤسس بيانات الفروع فقط. لا توجد بعد فواتير أو حركات مخزون أو تقارير تشغيلية، ولا يثبت FK اكتمال عزلها. قبل تنفيذ كل حالة استخدام في P05–P10 يلزم:

1. تمرير الفرع المقصود صراحة والتحقق من صلاحية المستخدم عليه داخل الخدمة، بما يشمل أي استدعاء مباشر دون الواجهة. لا يعتمد التفويض على قائمة الفروع المعروضة أو تغيير متغير عام.
2. تثبيت فرع المستند والتحقق من توافق مستودعه وحركاته ومراجعه. عمليات التحويل بين الفروع تحتاج سياسة واعتماداً واختبارات تحفظ الكمية والقيمة وتمنع الأثر الجزئي.
3. تطبيق نطاق الفرع في EF وتقارير Dapper، مع تقرير شامل لفروع التاجر للمخول فقط وفصل العملات. لا تجمع العملات اسمياً بسبب جمع الفروع.
4. ربط تدقيق العملية بفرعها ومصدرها ضمن تصميم المستند والتدقيق، واختبار مخزون وتقارير وصلاحيات فرعين ببيانات مختلفة.

سياسة منح الموظف فروعاً متعددة أو نطاق كل الفروع ستفصل قبل واجهة إدارة المستخدمين والعمليات؛ لا يمنح المدير أو الكاشير نطاقاً إضافياً تلقائياً. دعم المخطط لعدة فروع ليس إتماماً لهذه الوظائف.

## الاتصال والتشغيل

الأساس الحالي خادم محلي وأجهزة Windows على LAN، دون احتياج الإنترنت للتشغيل المحلي. قاعدة واحدة للتاجر تعني خادماً مشتركاً لفروعه المتصلة به.

الفرع الجغرافي البعيد يحتاج مسار اتصال آمناً بالخادم، يحدد عند تجهيز نشره مع اختبار الاعتمادية والانقطاع. لا توفر هذه الحزمة خدمة سحابية أو VPN داخل المنتج أو قواعد فرعية مستقلة أو مزامنة. عند انقطاع المسار إلى الخادم، تتعذر العمليات التي تحتاج قاعدة البيانات حتى عودة الاتصال. لا تثبت آلية اتصال أو عمل دون اتصال اعتماداً على صور الواجهة القديمة.

## التحقق وحدود الاعتماد

اختبار نموذج EF يفحص توليد هوية الفرع واستمرار قيد المنشأة الواحدة ومراجعها. توجد اختبارات SQL للترقية مع بيانات قديمة، ولإعداد فاشل ثم ناجح، ولإنشاء فروع مصرح بها، ورفض غير المصرح والمرجع غير الموجود، والتزامن، وفشل التدقيق، والرجوع الآمن، وفصل قواعد تاجرين.

اختبارات SQL لم تنفذ بسبب حجب تنزيل خادم الاختبار؛ لا نستنتج نجاحها من البناء أو توليد SQL. الأوامر والنتائج الفعلية في [دليل SQL](database.md) و[تقرير P03](database-status.md). لا تطبيق لهذه الترقية على قاعدة عميل في هذه الجلسة.
