# P04 — خطة النواة المحاسبية وحالة البداية

التاريخ: 2026-10-30. الفرع: Feature-account-system. إذن البداية: U8. الحالة: قيد التنفيذ؛ لم يكتمل محرك القيود أو تحويل العملات أو الضريبة بعد.

## بوابة الدخول والدليل

أبلغ المستخدم بنجاح تشغيل GitHub Actions لـb0439fa. راجعنا workflow ومشغل اختبارات SQL الذي يرفض التجاوز والفشل وصفر اختبارات. اعتمد تأسيس P03 بهذا الدليل مع توثيق أن API محجوب، وأن ملف TRX البعيد لم ينزل في هذه الجلسة. تغطية الأساس وحدوده في [تقرير P03](database-status.md). لم تعتمد بهذا الإذن السياسات المالية المفتوحة في DEC-001،002،004،006،008.

## ما نفذ في بداية P04.1

أضيف CurrencyAmount كقيمة غير قابلة للتعديل في Domain. تجمع قيمة decimal وهوية عملة موجبة داخل قاعدة التاجر، وتمنع جمع/طرح عملتين مختلفتين، وتكشف تجاوز سعة decimal بدلاً من إرجاع رصيد تالف. تسمح بالقيم السالبة لتمثيل فروق وأرصدة حسابية؛ لا تسمح هذه القيمة وحدها بسطر قيد سالب أو تجاوز أي قاعدة ترحيل.

تحفظ العمليات القيمة العشرية دون تقريب خفي. العكس هنا قلب إشارة القيمة فقط؛ ليس إلغاء مستند أو قيد. لا تختار عملة أساس أو معدل صرف، ولا تثبت دقة تخزين أو ضريبة، ولا تتصل بقاعدة البيانات. هوية العملة محلية لقاعدة التاجر؛ لا يستخدم هذا الكائن لدمج قواعد تجار مختلفين.

اختبارات البداية 7 حالات: رفض هوية صفر/سالبة، حفظ الدقة في الجمع والطرح، رفض خلط العملات ولو تساوت القيم الاسمية، عكس القيمة مع بقاء العملة، كشف التجاوز العددي، ورفض معامل مفقود. لا تحسب هذه الاختبارات نجاح SC-01 كاملاً؛ رأس القيد وسلامة الحسابات والفترات لم تنفذ بعد.

## القرارات المطلوبة قبل الاستكمال المالي

وصلت إجابة U9 عن السؤالين؛ تحديث الحالة:

1. تحديث U10 لـDEC-002: اعتمد المستخدم عملة الأساس مرجعاً، وحفظ مبلغ العملية وعملتها وسعرها التاريخي وما يعادلها، دون إعادة كتابة الأصل عند تغير السعر. يدعم النموذج سعراً صريحاً من عملة العملية إلى الأساس؛ لا يختار سعراً تلقائياً أو يعكس سعر زوج آخر ضمناً. تفاصيل أسعار الأزواج والتسديد الجزئي وفروق الصرف وإعادة التقييم ستوثق بأمثلة قبل ترحيلها. حالة عدم الاعتماد السابقة تخص U9 فقط.
2. اعتمد U9 بداية DEC-004: منزلتان للعملات الأولية ودقة معروفة للعملات الإضافية قبل الاستخدام، وتقريب نصف بعيداً عن الصفر (100.005 إلى 100.01، و-100.005 إلى -100.01). أضيف Round صريح يحافظ على العملة ولا يعدل الأصل. تقبل الدالة دقة decimal التقنية 0–28؛ لا يعني هذا اعتماد 28 منزلة لأي عملة أو تخزين SQL. دقة أسعار الصرف أعلى وتثبت تقنياً مع سياسة التحويل، وتوقيت تقريب السطر والضريبة والإجمالي وتوزيع الفروق لا يزال مفتوحاً. لا تقريب تلقائي للعمليات الوسيطة.

بعد الإجابة يحدّث سجل القرارات وتنفذ سياسة القيم والعملات باختبارات أمثلة معتمدة وMigration عند تغيير دقة التخزين. قبل الضريبة والافتتاح والعكس تستكمل أسئلة DEC-001،006،008 بأمثلة موجزة؛ لا نعتمدها بمجرد موافقة على أحد السؤالين أعلاه.

### تحديث U9 — التقريب

بعد اعتماد بداية التقريب، شُغلت Domain.Tests بالبناء عبر `dotnet test tests/HisabTak.Domain.Tests --no-restore --configuration Release -m:1 -nr:false --logger trx`: نجحت 25 حالة دون فشل أو تجاوز، ومنها 8 حالات جديدة للتقريب الموجب والسالب وقيم ما قبل/بعد النصف وثبات النتيجة وعلاقتها بالعكس ودقة العملات الإضافية ورفض الدقة خارج حدود decimal. لم يعاد في هذا التحديث تشغيل SQL محلياً أو بقية اختبارات الحل؛ أعداد 39/13 أعلاه تخص تشغيل بداية P04 السابق. لم تتغير الحزم أو قاعدة البيانات. يبقى قرار عملة الأساس قيد الشرح، فلا يبدأ تحويل العملات أو الترحيل بناءً على موافقة التقريب وحدها.

### تحديث U10 — القيمة التاريخية بعملة الأساس

اعتمد المستخدم مرجع عملة الأساس بعد الشرح، مع ترك سياسة التسديد لتحديد لاحق. أضيف BaseCurrencyValuation كقيمة غير قابلة للتعديل في Domain، تضم المبلغ الأصلي وعملته وسعراً موجباً من وحدة عملته إلى وحدات الأساس وتاريخ العملية والقيمة الدقيقة الناتجة. يحافظ النموذج على القيم الوسيطة دون تقريب خفي، ويمكن تقريب القيمة الناتجة صراحة وفق دقة العملة المعتمدة. إذا كانت عملة الأصل هي الأساس نفسها فلا يقبل إلا سعر 1؛ يرفض هوية أساس غير صالحة والأصل المفقود وتجاوز سعة decimal.

تثبت الاختبارات مثال 100 USD × 3.8 = 380 SAR، وأن إنشاء تقييم لاحق بسعر 4 لا يعدل تقييم السعر السابق، وأن دقة سعر 3.80000001 لا تختزل إلى منزلتين قبل الضرب، واتساق إشارات القيم والصفر وحدود التحقق. هذه لقطات قيم داخل الذاكرة وليست حتى الآن سجلات مالية محفوظة في SQL. سيحفظ نموذج القيود/المستندات القيم التاريخية ومرجع عملة أساس المنشأة عند تنفيذ التخزين، دون اختراع جدول منفصل لا يرتبط بعملية. لم تكتمل شاشة اختيار عملة الأساس أو قفل تغييرها بعد أول ترحيل أو التسديد أو إعادة التقييم. لم يتغير نموذج EF أو Migrations في هذه الحزمة.

عرض اقتراح مستقل على المستخدم: تسجيل فرق التسديد الفعلي في حسابي أرباح وخسائر صرف، ومعالجة الجزء المسدد فقط في التسديد الجزئي، بمثال دين 100 USD سجل بقيمة 380 SAR ثم سدد بـ400 SAR دون رسوم أو إعادة تقييم. كانت الموافقة معلقة في تسليم U10، ثم وصلت واعتمدت كمصدر U11 أدناه.

تحقق تحديث U10: نجح بناء الحل الكامل دون أخطاء أو تحذيرات، ونجحت 36 حالة Domain و7 Application و15 Infrastructure؛ الإجمالي المحلي 58 ناجحة و13 SQL متجاوزة من 71. يتضمن Domain إحدى عشرة حالة جديدة للقيمة التاريخية. لم تنفذ اختبارات SQL محلياً، ولا نستنتج نتيجة تشغيل GitHub الجديد من نجاح التشغيل السابق لـb0439fa. لم تتغير ملفات المصدر الأصلية أو حزم المشروع أو Migrations.

### تحديث U11 — حساب فرق التسديد

اعتمد المستخدم حسابين مستقلين لأرباح وخسائر الصرف ومعالجة الجزء المسدد فقط. أضيف ExchangeSettlementCalculation لحساب القيم الدقيقة لدين لم يُعد تقييمه ودون رسوم، مع تحديد اتجاهه Receivable/Payable. يستقبل القيمة التاريخية للدين، والجزء المراد إغلاقه بعملة الدين، وقيمة الدفع الفعلية مقدرة بعملة الأساس نفسها. لا يستنتج الجزء المسدد من مبلغ الدفع وحده، ولا يخلط وحدات العملات.

قيمة الجزء التاريخية = الجزء المسدد × السعر التاريخي إلى الأساس. للدين المستحق للتاجر، فرق الدفع الفعلي عن القيمة التاريخية ربح إذا كان موجباً وخسارة إذا كان سالباً؛ وللدين عليه ينعكس الاتجاه. يعيد النموذج قيم Gain وLoss غير سالبة وبعملة الأساس، والمبلغ المتبقي بعملة الدين؛ لا يسجل ربحاً وخسارة معاً. مثال جزئي: تسديد 50 USD من دين 100 USD بسعر تاريخي 3.8 بقيمة فعلية 200 SAR يغلق قيمة تاريخية 190 SAR ويعطي 10 SAR ربحاً للقبض أو خسارة للدفع، ويبقي 50 USD.

هذه نتيجة حسابية غير قابلة للتعديل، وليست سجل تسديد في SQL أو إقفالاً فعلياً للذمة. يجب أن تستدعي خدمة التسديد لاحقاً الحساب مع الرصيد المتبقي الصحيح داخل معاملتها وتمنع إعادة التطبيق والتجاوز تحت التزامن. السعر التاريخي والقيمة الأصلية لا يعدلان. لا توجد إعادة تقييم أو رسوم أو شطب أو دفع صفري في هذا الحساب، ولا تقريب خفي. تخصيص القيمة الدفترية المقربة وباقي التقريب في آخر تسديد يحتاج سياسة واختبارات قبل استخدام النتائج للترحيل. عند الربط الفعلي يلزم اختيار حسابين منفصلين وصالحين لأرباح وخسائر الصرف؛ لم تخترع هذه الحزمة أرقام حسابات أو تضف حساباً غير معتمد إلى Seed.

أضيفت 16 حالة اختبار لاتجاهي الربح والخسارة والتعادل والجزئي وبقاء الأصل، ورفض جزء غير موجب/أكبر من الدين أو عملة مخالفة أو دفع غير موجب أو مدخل مفقود/اتجاه غير معروف. إذا كان الدين نفسه بعملة الأساس فلا يحول الحساب زيادة الدفع عن أصله إلى ربح صرف تلقائي؛ يرفضها لأنها تحتاج معالجة مختلفة. طلب حسم أساس الافتتاحيات والفترات والعكس قبل تنفيذ التخزين المالي؛ لم تصل الإجابات وقت كتابة هذا القسم.

### تحديث U12 — الافتتاح والفترات والعكس

اعتمد المستخدم القيد الافتتاحي دون جمع رصيد افتتاحي آخر معه، ومنع الترحيل بالمغلق والعكس بالمفتوح وإعادة الفتح بصلاحية وتدقيق. أضيفت حماية تاريخ القيد ضمن حدود الفترة شاملة اليوم الأول والأخير، ومنع الفترة الموقوفة أو المحذوفة. Close يسجل مستخدم الإقفال ووقت UTC، وReopen يزيل علامة الإقفال الحالية دون حذف سجل التدقيق التاريخي. ترفض العمليات المتكررة للحالة نفسها.

تنفذ IFiscalPeriodService الإقفال وإعادة الفتح بصلاحيتين مستقلتين ACCOUNTING.PERIOD.CLOSE وACCOUNTING.PERIOD.REOPEN، مع معاملة SQL وقفل HisabTak.Accounting.Periods وrowversion. يحفظ التدقيق والحالة معاً، ويتراجع تغيير الحالة إن فشل التدقيق. يجب أن تستخدم خدمة ترحيل القيود المستقبلية القفل نفسه وتعيد فحص الحالة بعد اكتسابه؛ وجود خدمة الفترات وحده لا يمنع سباق ترحيل غير منفذ بعد. يضيف Seed الصلاحيتين تحت المحاسبة ويمنحهما للمالك، دون منح الكاشير/المحاسب/مدير الفرع تلقائياً. يجب تشغيل seed بعد الترقية لقاعدة موجودة حتى تتاح الصلاحيات الجديدة.

تضيف Migration الرابعة ProtectFiscalPeriodClosure قيد اتساق: المفتوح بلا بيانات إقفال، والمغلق بوقت ومستخدم إقفال. لا تعيد كتابة بيانات قديمة؛ ستفشل الترقية إذا كانت حالتها مخالفة وتحتاج فحصاً إدارياً. Down يزيل القيد فقط. لم تعدل Migrations السابقة، ولا يوجد حذف لجدول أو حقل أو بيانات.

JournalDraft مسودة حسابية غير قابلة للتعديل تضم نوع Standard/Opening/Reversal، وفرعاً وهوية مصدر تقنية مستقلة، وسطورا محددة الجانب والحساب وقيمتها التاريخية. تمنع القيد الفارغ أو أحادي السطر أو غير المتوازن بعملة الأساس، ولا تجمع عملات الأساس المختلفة. التوازن يستخدم قيم BaseCurrencyValuation الصريحة، مع إبقاء الأصل لكل سطر؛ تتوازن عملية الصرف المعتمدة مثل مدين 400 SAR ودائن 100 USD بسعر 3.8 ودائن فرق 20 SAR. لا يمثل تحقق التوازن وحده تحقق صلاحية الحساب أو عملته أو فرعه؛ تلزم قراءتها من SQL في خدمة الترحيل.

CreateOpening يميز الافتتاح كي تحتسبه التقارير من السجل فقط لاحقاً، ولا يقرأ Account.OpeningBalance أو يصفره. Reverse يولد مسودة ذات مرجع هوية الأصل وفرعه وأسعاره نفسها وجوانب معكوسة، بتاريخه الجديد في فترة مفتوحة، دون تغيير الأصل. SourceKey معرف تقني للمصدر، وليس سياسة ترقيم EntryNumber أو منع تكرار مخزن. لا توجد جداول JournalEntries/JournalLines بعد؛ تحقق وجود الأصل ومطابقة هوية الفترة وقفلها، ومنع التكرار تحت التزامن، وحفظ القيد الافتتاحي مرة واحدة وتوازن التقارير لم تنفذ بعد، ولا تعتبر هذه الدوال ترحيلاً أو عكساً فعلياً.

أضيفت اختبارات Domain لحدود الفترة والمغلق وإعادة الفتح والحالات غير الفعالة ووقت UTC، ومسودة الافتتاح والعكس والتوازن وأسعار العملات وعدم تعديل الأصل أو السطور. أضيفت 3 اختبارات SQL للصلاحيتين المنفصلتين والتدقيق، والإقفال المتزامن لمرة واحدة، والتراجع عند فشل تدقيق إعادة الفتح. توسع اختبار الترقية للحفاظ على فترة موجودة، واختبار الرجوع لعزل ترقية الفترات عن ترقية الفروع. لم تنفذ اختبارات SQL الجديدة محلياً؛ تحتاج نتيجة CI الجديدة ولا يغطيها نجاح P03 السابق. سيعرض قسم النتائج بعد تشغيل الاختبارات المحلية.
